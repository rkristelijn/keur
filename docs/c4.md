# C4 model

The C4 views below describe keur as it is built: a single compiled binary
(`bin/keur`) invoked by git hooks, reading rule data and config, deciding a
verdict over staged files. Grounded in `src/keur/main.cpp`, `src/keur/cmd/*`,
`src/keur/adapters/*`, `src/keur/report/report.*`, `src/rules/rule_engine.*`,
and `config/keur.toml`.

## Level 1: System context

```mermaid
C4Context
    title keur - system context

    Person(dev, "Developer", "Commits and pushes code, some of it AI-generated")

    System(keur, "keur", "Single C++ binary. Deterministic guardrails run as a git gate.")

    System_Ext(git, "git", "Version control. Invokes keur via pre-commit / pre-push hooks.")

    Rel(dev, git, "git commit / git push")
    Rel(git, keur, "runs hook stub: exec keur check --tier ...")
    Rel(keur, git, "queries staged files, resolves hooks dir")
    Rel(keur, dev, "prints verdict PASS / WARN / BLOCK, exit code")
```

The developer runs git as usual. git invokes the installed hook stub, which
execs `keur check`. keur reads the staged files back from git, decides, and
reports. A blocking verdict returns exit code 1, which stops the commit or push.

## Level 2: Container

```mermaid
C4Container
    title keur - containers

    Person(dev, "Developer", "")
    System_Ext(git, "git", "Invokes hooks, provides staged files")

    System_Boundary(keur_sys, "keur") {
        Container(bin, "keur binary", "C++20 / RE2", "hook, scan, check, policy, version subcommands")
        ContainerDb(rules, "Rule data", ".rule files under rules/", "pattern / presence / absence rules, grouped by category")
        ContainerDb(cfg, "Config", "config/keur.toml", "policy thresholds, tier scanner lists, tool inventory")
    }

    Rel(dev, git, "commit / push")
    Rel(git, bin, "exec keur check --tier")
    Rel(bin, git, "git diff --cached, git rev-parse --git-dir")
    Rel(bin, rules, "loads rules (KEUR_HOME/rules, KEUR_RULES_DIRS)")
    Rel(bin, cfg, "resolves + reads thresholds (XDG, KEUR_HOME, --config)")
    Rel(bin, dev, "verdict + findings on stderr/stdout")
```

The binary is self-contained. Rule data is external `.rule` files resolved from
`KEUR_HOME/rules` and `KEUR_RULES_DIRS`. Config is `keur.toml`, resolved through
the XDG global path, `KEUR_HOME`, or an explicit `--config`.

## Level 3: Component (inside the keur binary)

```mermaid
C4Component
    title keur binary - components

    System_Ext(git, "git", "")
    ContainerDb(rules, "Rule data", ".rule files", "")
    ContainerDb(cfg, "Config", "keur.toml", "")

    Container_Boundary(bin, "keur binary") {
        Component(main, "main / dispatch", "main.cpp", "argv -> subcommand table (unordered_map of handlers)")

        Component(cmd_check, "cmd::check", "cmd/check.{h,cpp}", "staged files -> rule engine -> policy_evaluate -> verdict")
        Component(cmd_scan, "cmd::scan", "cmd/scan.{h,cpp}", "directory scan -> findings -> report")
        Component(cmd_hook, "cmd::hook", "cmd/hook.{h,cpp}", "install / global / status / remove hook stubs")
        Component(cmd_policy, "cmd::policy", "cmd/policy.{h,cpp}", "config resolution + policy explain")

        Component(engine, "rule engine", "src/rules/rule_engine.*", "RE2 load / match / scan, emits RuleFinding")
        Component(report, "report provider", "report/report.*", "finding JSON, JSONL / compact / verbose, colour")

        Component(a_git, "Git adapter", "adapters/git.*", "the only git spawn site")
        Component(a_fs, "Fs adapter", "adapters/fs.*", "the only filesystem mutation site")
        Component(a_proc, "Proc adapter", "adapters/proc.*", "the only external-process spawn site")
    }

    Rel(main, cmd_check, "check")
    Rel(main, cmd_scan, "scan")
    Rel(main, cmd_hook, "hook")
    Rel(main, cmd_policy, "policy / version")

    Rel(cmd_check, a_git, "staged_files()")
    Rel(cmd_check, engine, "rules_scan_files()")
    Rel(cmd_check, cmd_policy, "resolve_config / policy_load")

    Rel(cmd_scan, engine, "rules_scan_dir()")
    Rel(cmd_scan, report, "report_findings()")

    Rel(cmd_hook, a_git, "hooks dir, config query")
    Rel(cmd_hook, a_fs, "write / remove stubs")
    Rel(cmd_hook, a_proc, "git config side effect")

    Rel(cmd_policy, cfg, "read thresholds")
    Rel(engine, rules, "load .rule files")
    Rel(a_git, git, "popen(git ...)")
```

Component notes, grounded in the code:

- `main.cpp` dispatches on `argv[1]` through an `unordered_map` of handlers.
  `version` and `help` are handled inline; the four verbs delegate to the `cmd`
  layer.
- `cmd::check` gets staged files through the Git adapter, loads rules from the
  resolved rule directories, scans in-process with the rule engine, and calls
  the pure `policy_evaluate`.
- `cmd::scan` scans a directory and hands findings to the report provider, which
  owns the output format.
- `cmd::hook` performs all I/O through the injectable `Git`, `Fs`, and `Proc`
  adapters (the `HookDeps` bundle).
- `cmd::policy` resolves `keur.toml` and reads `block-at` / `warn-at` / `version`.
- The three adapters are the only places keur touches git, the filesystem, or
  external processes. This is enforced by rule KEUR-ARCH-001.
