# KEUR — Handover / Session State (2026-09-16)

Snapshot voor voortzetting op een andere AI. Bevat: wat er vandaag gebouwd is,
wat werkt (met bewijs), openstaande wensen, en de volgende stap.

## Waar we staan (kort)

KEUR heeft nu een **native, gecompileerde rule-engine** (RE2, C++), gemodelleerd
naar cpm's `src/rules/rule_engine.cpp` maar clean geschreven in keur. Dit loste
de snelheidsblokker op: de shell-engine deed ~5 min over de volledige cpm-corpus,
de native engine doet **0.16s** (bewezen, zie hieronder).

## Vandaag gebouwd (met bewijs)

### Native rule-engine — `src/rules/`

- `rule_engine.h` / `rule_engine.cpp` — parser + RE2 single-pass scanner.
  Engines: `pattern`, `presence`, `absence` (~99% van de cpm-corpus).
  Long-tail (`file-absence/presence`, `extract-duplicates`, `block-absence`)
  wordt gemeld als unsupported, niet stil genegeerd.
- `main.cpp` — CLI `keur-rules --files <f...>` of `--dir <root>`, emit KEUR
  Finding JSON (één object per regel).
- `Makefile` — bouwt `bin/keur-rules`, linkt RE2 + abseil (Homebrew/Linux).
- `docs/adr/ADR-001-native-rule-engine.md` — de ADR (define-left, V-model).

Design-features overgenomen van cpm: single dir-walk, single read per file,
extension/filename-index voor dispatch, `content_contains` literal pre-filter,
pre-compiled RE2, `keur:ignore [<id|category>]` inline suppression (token-exact,
zodat `SEC-04` niet `SEC-043` onderdrukt).

### Bewezen resultaten (deze sessie)

- Build: `cd src/rules && make` → `bin/keur-rules` (clang, C++20, RE2 via brew).
- Snelheid: volledige cpm-corpus (959 rules / 1926 patterns) over 5 fixtures:
  **0.161s** (was 5min in shell). cpm zelf doet ~0.5s.
- Correctheid: FL-SEC-011, GO-SEC-012, SEC-023, FA-QUAL-011 vuren op de juiste
  files; keur-eigen KEUR-SEC-001 vuurt op een .pem private key.
- Suppression: `nosup.py` = 5 findings, `sup.py` met `keur:ignore` = 0.
- cpm-rule hergebruik werkt ongewijzigd via `KEUR_RULES_DIRS=~/git/hub/cpm/rules`.

### Wrapper

- `scanners/rules.sh` is nu een dunne wrapper: roept `bin/keur-rules` aan
  (native), valt terug op `lib/rules.sh` (shell, traag maar correct) als de
  binary niet gebouwd is of `KEUR_NO_NATIVE=1`.

## Rule-format (cpm-compatibel, bevestigd)

Zelfde YAML-ish schema als cpm: `id, title, category, severity, engine,
target{extensions, filenames, exclude_paths, content_contains}, patterns[{regex,
message}], fix`. Keur voegt optioneel `action` (block/warn/advisory) en
`confidence` toe; zonder die velden mapt de engine `severity` → action
(error/critical→block, warning→warn, info→advisory). RE2-regex, dus zelfde
semantiek als cpm.

## OPENSTAANDE WENS (belangrijk — expliciet gevraagd)

**"Kunnen we helemaal zonder shell scripts in keur?"** — JA, dit is de gewenste
richting. Rationale: we bewezen vandaag dat shell de verkeerde tool is voor de
hot path (5min→0.16s door naar C++ te gaan); die logica geldt breder.

Huidige shell-footprint (~867 regels, 13 scripts) + embedded Python in eval:

```text
lib/rules.sh        213   (shell rule-engine — kan WEG, vervangen door native)
eval/evaluate.sh    128   (eval-harness — Python-heavy; → C++ of los tool)
eval/gen-cases.sh    75   (Ollama case-gen — kan los blijven of C++/py tool)
lib/check.sh         69   (de gate — hot path, kandidaat voor C++)
lib/hook.sh          66   (hook install/manage — kandidaat voor C++ subcommand)
eval/loop.sh         63   (meetlus)
scanners/pii.sh      55   (pii scanner — kandidaat voor native)
eval/gen-batch.sh    45
eval/build-index.sh  45   (Python)
scanners/rules.sh    40   (wrapper — verdwijnt als alles native is)
lib/common.sh        36
lib/policy.sh        20   (policy engine — hot path, C++)
lib/scan.sh          12
bin/keur             (bash entrypoint → wordt C++ main met subcommands)
```

### Voorgesteld gefaseerd plan (geen big-bang; vermijd de rabbithole)

1. **Engine staat al native.** ✓
2. **`keur` entrypoint → C++ `main`** met subcommands (scan/check/hook/policy),
   zoals cpm één binary is. Shell `bin/keur` + `lib/*.sh` verdwijnen stap voor
   stap naarmate subcommands landen.
3. **check/policy naar C++** (hot path, gate <3s): lees staged diff, roep engine
   in-proces aan (link `rule_engine.o` direct i.p.v. via CLI), pas policy toe
   (block-at/warn-at, categories), exit-code. Geen proces-spawns meer.
4. **pii scanner naar C++** (of als rule-category in de engine).
5. **hook install** als C++ subcommand (schrijft de git hooks; hooks zelf mogen
   een one-liner blijven die `keur check` aanroept — dat is onvermijdelijk shell
   in .git/hooks, maar triviaal).
6. **eval-harness**: build-index + evaluate + loop. Python is hier defensibel
   (JSON, corpus). Optie: los `keur-eval` C++ tool, of Python behouden als
   "tooling" buiten de kern-binary. Beslissing openlaten.

Grens: de git-hook files in `.git/hooks/` MOETEN een klein shebang-script zijn
(git roept ze zo aan), maar dat kan een 1-regel `exec keur check --tier ...` zijn.
"Geen shell" = geen shell-LOGICA in de kern; de hook-stub is onvermijdelijk.

## Zelf-leer-loop status (uit eerdere sessie-context)

- MEETLUS (`loop.sh`+`evaluate.sh`): werkt. Draaide eerder 0.94 precision /
  0.48 recall (recall laag want alleen pii-scanner deed werk; nu kan de native
  rule-engine mee).
- case-generator (`gen-cases.sh`, Ollama fictieve cases): werkt.
- OPTIMISER (Ollama muteert rules, benchmark beslist): BESTAAT NIET (M3-T305).
- BLOKKER voor zinvol trainen: corpus verwacht rule-IDs `SECRET-AWS-001`,
  `PII-EMAIL-001`, `CBI-HOSTNAME-001` (22× elk) die NIET in keur/cpm bestaan.
  Custom rules met die IDs moeten eerst gebouwd (dan scoort eval op exacte
  rule-ID i.p.v. category-agnostisch "flagt keur iets").

## Volgende stap (aanbevolen)

Kies één: (a) `keur` entrypoint → C++ main met `scan`/`check` subcommands die de
engine in-proces linken (grootste stap naar "geen shell"), of (b) eerst de
custom secrets/pii/cbi-rules bouwen die het corpus verwacht zodat de meetlus
zinvol wordt. (a) volgt de "geen shell"-wens; (b) deblokkeert de leer-loop.
