# ADR-037 — Difficulty as an agent briefing: emit the gate's rules up front, not just enforce them after

@id ADR-037

## Status

Proposed · 2026-09-29 · Coverage: none
· Relates to: ADR-011 (project profile — the axes that decide what blocks),
ADR-026 (rule maturity levels — which rules are active per band),
ADR-035 (self-explaining findings — the *after-the-fact* explainer),
ADR-036 (`keur learn <RULE>` — on-demand per-rule rationale),
`docs/design/doom-level-select.md` (the difficulty chooser),
`docs/design/vision.md` (copilot for coding and vibe-coding)

## Context

keur is a **gate**: staged files → rule engine → findings → deterministic policy
→ PASS/WARN/BLOCK. Everything keur does today happens *after* the code is written
— the commit is attempted, the hook fires, the LLM (or human) is told what is
wrong. ADR-035 and ADR-036 sharpen that after-the-fact feedback (clear errors,
`keur learn <RULE>`), all so "nobody reaches for `--no-verify`".

A collaborator raised the missing half: **you cannot only punish the LLM with a
gate after the fact — you also have to tell the agent, up front, which gates
exist and why.** When a developer drives an AI coding agent (Kiro, Copilot,
Cursor, Claude Code, …), the agent reads whatever context/steering file the repo
provides (`AGENTS.md`, `.github/copilot-instructions.md`, `CLAUDE.md`, a `.kiro`
steering doc). If keur's active rule set is *not* in that briefing, the agent
writes code blind to the gate, the hook blocks it, and the loop wastes a
round-trip — exactly the friction that trains people toward `--no-verify`.

This is the same **shift-left** argument ADR-011 already makes, applied one step
earlier. ADR-011 shifts *detection* left (block locally in a second, not in prod
in days). This ADR shifts *prevention* left again: don't just detect the slop
before commit — **stop the agent from generating it in the first place**, by
handing it the rules of the level it is playing on.

Today the difficulty a project picks (`docs/design/doom-level-select.md`, mapped
onto ADR-026's maturity band and ADR-011's profile axes) only affects the gate's
strictness. Nothing turns that choice into instructions the agent can read. The
knowledge exists — keur knows precisely which rules are active for the chosen
level — but it is trapped inside the binary until a commit trips it.

## Decision

**When a difficulty/profile is chosen, keur emits an agent briefing** — a
generated, human-and-AI-readable instruction file that states the active gates
and *why* — so an agent produces conformant code and the hook stays green. The
gate is unchanged; this adds a *pre-flight* artifact derived from the same
profile the gate already uses. One source of truth (the resolved profile), two
consumers (the gate that enforces, the briefing that informs).

### 1. `keur agents` — generate the briefing from the resolved profile

A new subcommand renders the active rule set for the current profile into an
instruction file:

```bash
keur agents                       # write the default briefing (see §2 target)
keur agents --target AGENTS.md    # explicit target file
keur agents --target copilot      # known flavour → .github/copilot-instructions.md
keur agents --print               # stdout only, write nothing (CI / inspection)
keur agents --check               # exit 1 if the on-disk briefing is stale vs profile
```

It is a pure function of the resolved profile (ADR-011 cascade) and the active
maturity band (ADR-026): `profile → active rules → briefing`. No new policy, no
new rule semantics — it *reads* what the gate would enforce and writes it down.
I/O stays at the edge (ADR-003): the render is pure, the file write is an adapter.

The difficulty chooser (`docs/design/doom-level-select.md`) offers to run this on
select: after you pick "KEUR Me Plenty", it can write/refresh the briefing so the
choice immediately reaches the agent, not just the gate.

### 2. The briefing — content contract

A generated, clearly-marked block (so hand-written guidance around it is
preserved on regeneration — a `BEGIN/END keur` fenced region, like a managed
block):

```markdown
<!-- BEGIN keur:agent-briefing (generated by `keur agents`; edit above/below, not inside) -->
## keur gate — what will block this commit (profile: standard · maturity 3 · tier-2)

This repo runs keur as a pre-commit/pre-push gate. Write code that passes it the
first time. Active rules at THIS level, and why they exist:

### Will BLOCK (fix before it is written)
- **Secrets** (KEUR-SEC-*): never inline credentials/keys/tokens; use env/secret store.
- **Command injection** (KEUR-CMDI-*): no shell string interpolation; use argv vectors.
- **SQL injection** (KEUR-SQLI-*): parameterised queries only.
  …one line per active blocking category, generated from the active rules…

### Will WARN (prefer to avoid)
- **File size** (KEUR-QUAL-*): keep files well under ~300 net lines.
  …active warn-tier categories…

### Not enforced at this level (raised by a stricter difficulty)
- Traceability coverage, coverage thresholds — active from maturity 4+.

Per-rule detail on demand: `keur learn <RULE-ID>` (ADR-036).
Do not bypass with `--no-verify`; fix what the message says.
<!-- END keur:agent-briefing -->
```

Content is generated from the active rules' own fields (title, category,
severity, action, `fix:`, CWE) — the same data ADR-035/036 already surface — so
the briefing and the gate can never drift: both read one rule set. The
"not enforced at this level" section is the pedagogical bit the collaborator
asked for: it shows *which* difficulty a rule belongs to, so the agent (and the
human) understand the level they chose and what a stricter one would add.

### 3. Target-file flavours (meet the agent where it reads)

Different agents read different files. `keur agents --target <flavour>` knows the
conventional locations; the generated block is identical, only the destination
differs:

| flavour | file |
|---------|------|
| `agents` (default) | `AGENTS.md` |
| `copilot` | `.github/copilot-instructions.md` |
| `claude` | `CLAUDE.md` |
| `kiro` | `.kiro/steering/keur-gate.md` |
| `cursor` | `.cursor/rules/keur-gate.md` |

Unknown/explicit paths are honoured verbatim (`--target docs/foo.md`). Multiple
targets in `keur.toml` let a repo emit several at once.

### 4. `--check` closes the loop with the gate

`keur agents --check` re-renders the briefing in memory and compares it to the
managed block on disk; exit 1 (with a diff) if they differ. This lets a repo run
it as a keur self-check / CI step so a profile change that isn't reflected in the
agent briefing is caught — the briefing is kept honest the same way the gate is.
Optionally a `KEUR-*` internal rule can flag "profile changed but briefing stale"
so keur guards its own promise (self-check tradition, AGENTS.md).

## Why not the alternatives

- **Hand-write `AGENTS.md` per repo**: drifts the moment the profile or the rule
  corpus changes; every repo re-derives the same thing by hand. Generation from
  the one source of truth is the whole point — no second copy to rot.
- **Point the agent at the raw `.rule` files / `keur scan` output**: the matcher
  data and JSONL findings are for the engine, not a briefing. An agent needs
  *intent and level context* ("secrets block here, traceability doesn't yet"),
  not regexes. The briefing is a rendered view, not a dump.
- **Only improve after-the-fact errors (ADR-035/036) and stop there**: that
  fixes the round-trip's *quality* but not its *existence*. Telling the agent up
  front removes the round-trip. Both halves are needed; this is the pre-flight
  half.
- **Bake it into the hook install**: install happens once; profiles and rule sets
  evolve. A regenerable command + `--check` keeps it current without reinstalling.

## Consequences

**Positive**
- The difficulty a project picks now reaches the *author* (human or AI), not only
  the *gate* — prevention shifts left, so the hook fires less because less slop
  is generated in the first place.
- One source of truth: the briefing is a rendered projection of the exact rule
  set the gate enforces, so guidance and enforcement cannot disagree
  (`--check` proves it).
- Deepens the vision's "copilot for coding and vibe-coding" — the agent is
  briefed on the rules of the level, not just penalised for breaking them —
  without weakening keur's author-neutrality (ADR-011): the briefing describes
  *code* rules, and applies identically whether a human or an AI reads it.
- Meets agents where they already read (AGENTS.md / copilot / claude / kiro /
  cursor), so adoption is a single command, no bespoke integration.

**Negative / cost**
- A new `cmd/agents.*` subcommand + a pure renderer over the active rule set +
  target-flavour path table. Modest, and it reuses ADR-035/036 rule-field access.
- Repos that hand-edit `AGENTS.md` must keep keur's edits inside the managed
  BEGIN/END block; content outside it is preserved, but the discipline must be
  documented (it is, in the block header).
- The briefing summarises (one line per active category) rather than listing
  every rule, to stay readable; `keur learn <RULE>` (ADR-036) remains the path to
  full per-rule detail. Summary granularity is a follow-up to tune.

## Follow-ups

1. `cmd/agents.{h,cpp}` — pure `render_briefing(profile, active_rules) → string`;
   adapter writes/updates the managed block in the target file.
2. Wire the difficulty chooser (`doom-level-select.md`) to offer
   `keur agents` on select, so choosing a level briefs the agent immediately.
3. `keur agents --check` as a CI/self-check step; optional `KEUR-*` internal rule
   for a stale briefing so keur guards its own pre-flight promise.
4. Add the flavour table to `config/keur.toml` (`[agents] targets = [...]`) so a
   repo declares which briefings to emit.
5. Document the pre-flight half in `docs/design/vision.md` (gate = enforce,
   briefing = inform — two consumers of one profile).
